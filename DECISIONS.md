## ITC Addendum

Ad-hoc ITC Map Builder for the Boardroom group. Intentionally isolated from the main app; deeper integration comes later. Isolation guarantees are documented in `docs/itc-isolation.md`.

- **Ad-hoc auth is a hard boundary.** ITC uses its own email+password (fixed `1111`) login, a separate `itc_participants` table, and a distinct HMAC-signed cookie (`itc_session`, path=`/itc`). The main `users` table and Supabase auth are never touched by the ITC flow. Matching emails do not link the two identities.
- **Cookie scoping.** `itc_session` is set with `path=/itc`, so browsers do not send it to any other route. Main middleware also short-circuits on `/itc/*` and never runs Supabase session refresh for those requests.
- **RLS deny-all on `itc_*` tables.** All ITC tables have RLS enabled with zero policies. The anon key cannot see them at all. Only the service role (via `/api/itc/*` server code) reads or writes. Participant scoping happens at the API layer, keyed off the `itc_session` cookie's `pid`.
- **Model selection.** `ITC_COACH_MODEL` defaults to `claude-sonnet-5`. Configurable via env so the model can be swapped without a deploy. User confirmed the model ID on 2026-08-11; if the API rejects it at runtime, override the env var.
- **Vercel Hobby-tier cron.** Removed the hourly cron entry from `vercel.json` (the endpoint stays for manual/future use). Hobby accounts only allow daily schedules.
- **Feature flag `ITC_DEMO_AUTH`.** When unset or not `"1"`, the entire `/itc/*` tree 404s via the ITC layout gate. This is how the feature is disabled in production without removing code.
- **`itc_worries.behavior_id UNIQUE NOT NULL`.** Schema enforces exactly one worry per behavior. API stage-machine also refuses to transition to `commitments` until every behavior has a worry.
- **`pillar_code` enum reuse.** ITC maps carry a BRAVEMAN pillar so the ad-hoc feature stays aligned with the main framework vocabulary. No new pillar taxonomy.

## ITC v2 Elevation

Multi-checkpoint upgrade. Judgment calls per checkpoint.

### Checkpoint A — infrastructure

- **Retry cadence.** `runItcCoachTurn` now attempts `generateObject` three times total (initial + 2 retries) before falling back to `generateText`. Chose 3 not 2 because the observed "no object generated" errors were transient in the reviewed session; two retries got us into cost/latency territory (each attempt is a full turn). If cost/latency hurts, drop to 2.
- **Text fallback returns action:null.** A prose-only reply cannot advance stages or save entries — the stage machine and rubric checks (Checkpoint C onward) rely on structured actions. Losing an action for one turn is preferable to a bogus one. The affirmation safety net in `sendCoachMessage` still fires, so goal-lock isn't blocked by a fallback.
- **Empty-turn / dedupe policy.** Guard runs after every coach turn (including the fallback path). Empty replies get one nudge-and-regen. Consecutive verbatim duplicates get one nudge-and-regen with an inline system-message hint. A second failure is accepted — the fallback path guarantees a non-empty string, so nothing empty ever hits the DB.
- **Formatting default is at the prompt.** Numbered-list-for-more-than-two-items and re-display-relevant-list-when-asking are now mandatory in the system prompt, not a UI post-process. Post-processing prose into lists would be brittle; instructing the model is cheaper and cleaner.
- **Live map panel scope for A.** Verified goal, behaviors, worries render live as they lock (columns 1–3). Hidden commitments (col 4) and Big Assumptions (col 5) still render as placeholders because no capture flow exists yet — those wire up in Checkpoint D. Review-stage rendering piggybacks on the always-on right-side panel; no chat recap needed on desktop, and the numbered-list default (1.2) covers mobile and any admin-only chat surface.
- **`/admin/itc` vs `/itc/admin` naming.** Instruction referenced `/admin/itc`; shipped route is `/itc/admin`. Kept the current route since it's already in production and admin nav links point at it. Rename can happen later without functional change.

### Checkpoint B — Column 2 pruning + 1:1 worry gate

- **Parked, not deleted.** Behaviors below the cap set `selected=false` rather than being removed. Guides emphasize the fuller picture is useful context even if only a subset gets a worry pairing. Kept a separate delete affordance for actual typos.
- **Single `prune_behaviors` action instead of batched park/unpark.** Coach emits one `keep_indices` array; server sets `selected=true` for those and `selected=false` for everything else. Atomic, single-turn, and lets the coach propose a whole reshaped set in one move. Alternative (individual park/unpark actions) would require multi-turn coach flow which the current one-action-per-turn schema doesn't support.
- **1-based indices in the schema.** The coach emits 1-based `keep_indices` matching the numbered list it sees in the context block. UUIDs would be reliable but hard for the model to output correctly; index-into-order is simpler and matches how the coach references the list conversationally.
- **Gates enforced in `advanceStage`, not in the client.** `behaviors → worries` refuses if selected count is <1 or >5; `worries → commitments` refuses if any selected behavior lacks a worry. Client-side "continue" button gates on the same rule, but the server is authoritative.
- **`itc_worries.behavior_id UNIQUE` already exists** (per the original addendum). Now paired with the server-side 1:1 gate — the DB constraint prevents two worries per behavior, the stage gate prevents advancement with any missing worry. Both fire.
- **No affirmation safety net at behaviors stage.** The manual "I'm done adding behaviors — continue" button is always available and the coach's prompt is explicit about emitting advance_stage on affirmation. The goal-stage affirmation net was needed because the coach was mid-turn between propose_goal and advance_stage; behaviors doesn't have that seam.

### Checkpoint C — worry depth (rubric + excavation + no false praise)

- **Rubric model = Haiku.** `ITC_RUBRIC_MODEL` defaults to `claude-haiku-4-5-20251001`. Sonnet is overkill for three binary judgments; Haiku is fast, cheap, and firm. Chose an env override so the rubric can be swapped without a deploy.
- **Three binary criteria, sum to 0–3.** is_fear, is_first_person_felt, touches_self_image. Score < 2 always rejects. Score 2 requires at least one prior attempt (i.e., at least one excavation pass). Score 3 locks immediately. Simpler than a continuous score and easier to explain to the coach in prompt.
- **`itc_worry_attempts` table.** Every `propose_worry` lands here with its rubric score and accept/reject state, so the excavation-pass count for a behavior is a cheap `count(*)` rather than transcript heuristics. Enables the "score 2 needs a second attempt" rule without special history walks.
- **Rejections surface to the coach as `[action rejected]` system messages.** Existing catch already writes those. The coach input now includes the last 3 for the next turn's context block. Alternatively I could inject as assistant turns — chose not to because they'd render in the coachee's chat panel.
- **No worry capture UI panel.** Worries are captured exclusively via the coach's `propose_worry` action. The reviewed session showed the coach happily accepting shallow worries when the man typed them freely; forcing every worry through the rubric via a coach turn keeps depth honest. If the coach breaks down completely and can't drive it, the fallback is: participant asks the coach to try again.
- **No-false-praise ban is duplicated in the prompt, not only in the voice-and-tone doc.** The reviewed session showed the model drifted into "brave," "raw," "things most guys never say out loud" praise at exactly the moment the rubric would have scored 1/3. Explicit list of banned praise phrases at the worry-stage instructions.
- **behavior_index vs. behavior_id in propose_worry.** Same reasoning as prune_behaviors: 1-based indices into a stable ordered list are easier for the model to output correctly than UUIDs. The context block shows the selected-behavior numbering explicitly.
- **Server error message is a coach instruction, not user-facing.** "worry not deep enough (score X/3)... Keep excavating with the coachee — do NOT re-propose the same text." The message is captured as a `[action rejected]` system message and only surfaced to the coach's next turn context. The coachee never sees the rubric score.

### Checkpoint D — columns 3–4, reveal, prioritization, test design

- **Two rubrics beyond the worry one.** Commitments rubric is binary-pass (self-protective + first-person, no productivity-blog phrasing); assumptions rubric is the same 3-criterion shape as worries (finished-then + first-person felt + lands in identity/Big Time Bad). Chose consistency with the worry pattern where possible; commitments got a pass/fail because "self-protective" is really the whole test.
- **Reveal beat and full walkthrough are separate.** `reveal_delivered` here tracks the brief gas-and-brake beat at the end of column 3 (v2 3.3b). The deeper immune-system walkthrough gets its own stage and its own `walkthrough_delivered` flag in the next commit. Keeping the two distinct so we can gate prioritize on the walkthrough while still letting the reveal happen mid-column.
- **`itc_assumption_commitments` join table.** Assumptions consolidate — one Big Assumption underwrites several commitments. Join table records which commitments an assumption covers; the map panel renders the coverage inline. Alternative (array column on itc_assumptions) would break relational hygiene and make coverage checks slower.
- **Coverage gate at `assumptions → review`.** Every commitment must be covered by at least one assumption link. Prevents advancing with orphaned commitments and forces the coach to consolidate honestly.
- **Prioritization uses recommend_ then select_ actions.** Coach recommends first (per v2 3.5 — inverted in the reviewed session), then the coachee's pick wins. Two actions so both signals persist and the map panel can render both "coach recommends" and "selected for testing" states clearly.
- **Test design action wiring deferred to Checkpoint E.** The four Appendix D fields and target_date already exist in `itc_tests`. Wiring a `propose_test` action + the target-date validation is straightforward but adds another set of moving parts. Prompt instructs the coach to walk the coachee through the four fields in prose meanwhile; migration path is a one-commit follow-up if E surfaces a real UX need.
- **Rubric feedback surfaces to coach the same way as worries.** Rejected `propose_commitment` and `propose_assumption` both throw with an instruction to rework rather than re-propose. `[action rejected]` messages accumulate in the coach's context via the same last-3 feed established in C.

## ITC State Rebuild — Checkpoint A (2026-08-18)

- **Native tool use replaces the marker + extractor pipeline.** Coach turn runs `generateText` with `tools:` bound to a `TurnScope`; content actions become `itc_action_proposals` cards, immediate actions apply server-side through existing stage guards. See `src/lib/itc/coach-tools.ts`, `src/lib/itc/coach-turn-tools.ts`. Marker parser + leakage regex + extractor LLM are still on disk behind `ITC_PIPELINE=legacy` and deleted once Checkpoint D passes.
- **Rubric-at-proposal-time, not at accept-time.** Worry and assumption depth rubrics run inside the tool's `execute()`. A rejected proposal never becomes a card. The tool result returned to the model names what failed and instructs recovery — this text is invisible to the coachee.
- **Multi-step tool use with `stopWhen: stepCountIs(2)`.** The coach gets one recovery step after a rubric rejection, in the same turn. Cost: one extra model call on rejected proposals. Chosen over next-turn feedback for UX (one exchange instead of a dead beat). If cost becomes prohibitive, revert path: set `stopWhen: stepCountIs(1)`, delete the recovery event-emitter branch, and feed the rejection reason as an `[action rejected]` system message on the coachee's next turn (matches the legacy pattern).
- **Rubric-rejection cap = 1 per turn, enforced two ways.** `stopWhen: stepCountIs(2)` caps model calls. `scope.rejectionsCount` inside `buildCoachTools` blocks any further proposal tool calls after the first rejection, regardless of type. Belt-and-suspenders.
- **On rejection, coach ends on a question and cannot re-propose in the same turn.** The rejection tool-result instructs the model that the coachee's answer supplies the depth, not the coach's rewrite. Enforced by prompt only; if the model ignores it we add a post-step check that fails the turn.
- **Visible-reply policy on rejection: last step only.** If a rubric rejection fired, the coachee sees only the recovery step's prose. Step 1's failed-draft prose is suppressed. Without a rejection, all step texts concatenate.
- **Two new turn-event types: `rubric_rejected_proposal` and `same_turn_recovery`.** Rich payloads (rejected text, rubric scores, is-fear/first-person-felt/touches-identity flags, recovery prose, ends-with-question boolean, step-by-step texts) so live sessions can be audited for whether recovery questions actually land.
- **Preamble no longer teaches marker syntax.** Marker docs replaced with a short "state changes go through tool calls" section and hard rules against referencing rubrics/validation/UI in visible prose. Per-stage prompts still reference the old marker names — legacy still runs if the flag flips; delete at Checkpoint D.
- **`docs/coach-voice-and-tone.md` gained two sections.** "Never reference the interface" and "Never reference validation, rubrics, or rejection" — comprehensive banned lists for both. Every coach turn loads this file; new sections apply immediately.

## ITC Form-First Layout Amendment (2026-08-18)

- **Audit overreach — depth_score + attempts columns dropped, then reinstated.** Migration `20260818000003_drop_depth_and_recommend.sql` removed `depth_score` from `itc_worries` and `itc_assumptions` and dropped `itc_worry_attempts` on the read that no live code wrote them. That read missed the Form-First rewrite spec's requirement that Continue at the depth stages is rubric-gated. Without the columns, a shallow worry ("I'm afraid of wasting time") passed Continue trivially — the exact failure the excavation loop exists to prevent. Migration `20260818000004_reinstate_depth_and_attempts.sql` puts back `depth_score int (0-3, nullable)` and adds `attempts int not null default 0` to both tables. `itc_worry_attempts` remains dropped (attempts is a column now, not a table).
- **Form-First-pure rubric mechanism.** The coach never writes `depth_score`. A deterministic server pipeline step (`src/lib/itc/rubric.ts::scoreWorryDepth`, cheap utility-model `generateObject` with a 3-criteria binary rubric) runs on every worry save/edit, stores the resulting 0-3 score, and increments `attempts`. Same class as the dedup step: the LLM computes, the server writes. The coach's reaction prompt then receives the score as INPUT so it can excavate at the right depth in prose; the coach never mentions the score.
- **Depth-gate rule.** For advancement out of `worries` (and later `assumptions`): pairing rule always AND `depth_score = 3` OR (`depth_score = 2` AND `attempts >= 2`). The two-attempts-at-depth-2 escape hatch prevents locking a man out when the rubric edge-cases a genuine fear.
- **Reply-in-thread deleted entirely.** `postThreadReply` server action, `EntryThread` reply textarea, and the `itc-thread-focus` broadcast are all gone. Reply-in-thread was a fourth "change the map" affordance that misled users: typing a corrected entry into a reply put text in a chat message, the reaction pipeline treated the reply as if it were the revised entry, the coach acknowledged it — but nothing landed on the map. The map now changes via exactly three affordances: edit the input directly, tap a chip, ask the dock. `EntryThread` is pure render (prose + chips).
- **Inputs are always editable, all stages.** Dropped the `readOnly={!isActive}` gate on goal and behavior inputs. Backward edits from later stages never destroy downstream entries; the next coach reaction on the active stage sees updated map state naturally. `entry_edited` turn event now carries a `stage_at_edit` field so back-edit patterns are auditable.
- **Stage intros moved client-side.** `seedStageIntroIfNeeded` deleted. `STAGE_INTROS` lives in `src/lib/itc/stage-intros.ts` as pure static text with a `({ goal }) => string` signature; `map-canvas` renders the interpolated version every render. Legacy stored canned intros are filtered at render via `LEGACY_INTRO_PREFIXES`. This eliminates the stale-quote class of bug — the "Column 2 works against 'jumping jacks'" persistence bug can no longer recur because no coach-authored surface bakes map text into stored prose.

## ITC Form-First Layout Amendment — Checkpoint C (2026-08-18)

- **Excavation loop extended to Column 4 (commitments).** Same shape as worries: user writes in an inline-editable input (one per worry, 1:1 pairing rule); server pipeline runs `scoreCommitmentDepth`, stores `depth_score` (0-3) + `attempts` on `itc_commitments`, coach reaction receives the score as prompt input for its prose and never mentions it. Migration `20260818000005` adds the columns.

New shape is three orthogonal booleans: `is_self_protective`, `is_first_person`, `is_not_productivity_platitude`. Score is the sum (0-3), same shape as `scoreWorryDepth`. No behavior change in the semantic bar — same three tests, cleaner counting.
- **Depth-stage reaction prompt is kind-aware.** The old prompt had worry-flavored examples throughout ("what part of you is on the line"). Now the depth branch splits by kind: worries push external → felt → identity; commitments push virtue → self-protection ("what are you keeping YOURSELF safe from?"). Same three-tier structure (shallow/medium/deep) with kind-specific example acknowledgments and excavation questions. Prevents the coach from asking "what fear" about a commitment or vice versa.
- **Renamed `justAdded.behaviorText` to `justAdded.pairedText`.** The paired context for a worry is a behavior, for a commitment is a worry, for an assumption is a commitment. The old name was worry-specific. The reaction prompt now labels the pairing correctly based on `kind`.
- **Continue gate for `commitments → assumptions`.** Pairing rule (every worry has a commitment) AND every commitment passes at 3/3 OR 2/3 with attempts ≥ 2. Deterministic — reads only the rubric-written metadata. Same rule as worries.
- **CommitmentsRow shows the paired worry AND behavior in the label.** Because the fear-flip-to-vow logic requires him to see what he's protecting himself from, the row surfaces both entries above the commitment input. Placeholder is `"I'm committed to never…"` to bias toward the self-protective form.

## ITC Form-First Layout Amendment — Checkpoint D (2026-08-18)

- **Excavation loop extended to Column 5 (Big Assumptions).** Full form-first flow now covers Columns 1-5: user writes, server rubric scores, coach reacts in prose, gate enforces depth. `scoreAssumptionDepth` (already in `rubric.ts`, previously unused) wired into a new `saveAssumption` server action. `depth_score` + `attempts` on `itc_assumptions` are populated by every save; Continue gate to `immune_system` blocks until every assumption passes at 3/3 or (2/3 AND attempts ≥ 2). No schema change — migration `20260818000004` already added the columns.
- **Many-to-many pairing keeps the ITC semantics honest.** Unlike C3 (worry→behavior, 1:1) and C4 (commitment→worry, 1:1), an assumption underwrites 1..N commitments via the `itc_assumption_commitments` link table. Real ITC maps often have one root belief keeping multiple commitments alive; forcing 1:1 here would drop information. UI: each assumption row carries a set of commitment chips the coachee toggles. `saveAssumption` clears links then reinserts atomically so the payload set is authoritative each save.
- **`saveAssumption` handles both add and edit through one action.** New assumption → `assumption_id` omitted from form → `addAssumption` inserts. Edit → `assumption_id` present → `updateAssumptionText` bumps attempts and clears the stale depth_score. `removeAssumption` is a separate destructive action; links cascade via FK.
- **Assumption-flavored depth prompt.** Replaces the generic "SCORE 0-1 / 2 / 3" placeholder in the depth-stage branch with kind-specific language about if-then form, first-person felt, and lands-in-identity-or-Big-Time-Bad. Shallow prompts push the "then" clause from forecast to identity ("if that happens, what does it MEAN about you?").
- **Depth-stage kind coverage complete.** The reaction prompt now has three specialized branches: worry (external→felt→identity), commitment (virtue→self-protection), assumption (finished-then→identity). The fallback branch is unreachable in practice; kept as a safety net.

## Goals Rebuild and Dashboard (2026-08-26)

Migrations `20260826000001_goal_source_and_split_cap.sql`,
`20260826000002_goals_rebuild_schema_and_rls.sql`,
`20260826000003_goal_needs_review_status.sql`.

- **Split cap over global cap.** Original `enforce_active_goals_cap_trg` capped active goals at 2 per user per quarter. `syncItcGoalToTracker` writes a goal when an ITC map is saved, but the tracker-link failure policy ("never block, log and retry") is right for transient failures and wrong for a structural cap that never resolves on retry. Fix: `goal_source` ENUM('user','itc') column + rewrite trigger to allow 2 user + 1 ITC (3 total) per quarter. `source='itc'` claims the third slot; `source='user'` insert is rejected at 2/2 user goals.
- **Backfill via `itc_maps.quarterly_goal_id`.** Rows created by `syncItcGoalToTracker` before the discriminator existed can be identified by the FK link in `itc_maps.quarterly_goal_id`. Backfill sets those to `source='itc'`; everything else defaults to `source='user'`.
- **Trigger fires on `source` change too.** Not just `status` + `quarter_start`. A source rewrite (`itc` → `user`) in the same active state would otherwise bypass the user-slot check. Cheap belt-and-suspenders.
- **Two-section /goals layout.** Regular goals (source='user') live in one section with full start-line / finish-line / how-you-know treatment. Adaptive Goal (source='itc') lives in a separate lean card that only renders when the coachee has an active ITC map. The Adaptive card does NOT display the goal text — the ITC map is the source of truth for that text, and duplicating it here would drift on edits. Card shows stage + behavior count + test count + link into the map. If no active ITC map, the Adaptive section shows an italic note; no CTA to build one (guys who want an ITC map find /itc; the goals page shouldn't recruit them).
- **`description` renamed to `desired_end_state`.** Both user-authored and ITC-mirrored goals use this column. User goals: their finish-line. ITC goals: the "I'm committed to getting better at ..." text. `current_state` / `how_youll_know` / `review_reflection` added as nullable columns; populated only for user goals. No backwards-compat alias; touched all 8 call sites atomically. Rationale: no legacy user cohort to preserve (product decision).
- **RLS narrowed from "community-mate read" to "leader-of-user read".** Goal text is more personal than a mission description and should not appear on community-facing surfaces (leaderboard, digests). Community peers no longer see each other's goal text. Leaders retain read access via existing `is_leader_of_target()` helper — they see member goals for coaching context, which matches the visibility model the leader disengagement/corrections views already use.
- **UTC canonical quarters.** `src/lib/scoring/quarters.ts` is the single source. Per-user-timezone plumbing across three surfaces (missions header, goals page, quarter-end cron, dashboard goal bands) adds more complexity than it removes ambiguity for the edge case of a user near local midnight on the four quarter boundaries per year. Everyone shares the same UTC quarter. `<QuarterCountdown />` shared component on `/missions` and `/goals` headers so the days-left number is always identical.
- **`needs_review` as a new status value, not a boolean.** Daily cron transitions any active goal whose quarter has ended into `needs_review`. Alternative was a `needs_review_at` timestamp on `quarterly_goals`, but that adds a nullable column that most rows never use and needs a special-case in every status-filtering query. Enum value is cheaper and self-documenting. Trade: enum-value additions in Postgres require a separate DDL statement (`alter type add value`) that can't be wrapped in a transaction with other DDL — done in its own migration file.
- **Review prompt is nudge, not gate.** Non-blocking dismissible prompt on `/today` and `/goals`. "Not now" hides for the current render only; no persisted dismissed-flag. Prompt reappears on next visit until the coachee answers Yes / Partially / No. Design intent: keep the app moving, not force a modal.
- **ITC goals surface on the review prompt too, but with a different variant.** They can't be closed from `/goals` (owned by the ITC map). The review prompt for a source='itc' needs_review goal shows "Open the map" instead of the Yes/Partially/No buttons — points the coachee back to the ITC done-stage close-out flow.
- **Dashboard as separate route, cards independently Suspenseful.** New `/dashboard` route, linked from `/me` (one prominent card at the top) rather than added to the mobile BottomNav — the nav is at its 5-slot ergonomic cap and adding a 6th would break the layout ergonomics. Each card is a separate async server component wrapped in Suspense so the slowest query (usually the full-history composite trend) doesn't block the whole page.
- **Recharts as the chart library.** Client-only (server-rendered charts require additional plumbing), so each chart is a small `"use client"` component that receives shaped data from the server card. Themed via brand CSS tokens (`--color-primary`, `--color-pillar-*`, `--color-warning`) so the dashboard matches the rest of the app in dark mode.
- **Empty states are prose, not empty axes.** Every card, if data isn't rich enough to draw, shows one plain sentence explaining what will appear once history builds up. Rationale: a man in his first week should see a dashboard that looks intentional, not broken. Two-week minimum for the trend charts (composite, mission follow-through) so the line has enough points to be meaningful.
- **ITC status card uses the service client.** `itc_maps` + `itc_participants` live outside the main-app user RLS scope (they FK to `itc_participants.user_id` but the tables themselves have their own RLS pattern). Service client is the established access path for cross-table ITC reads (see `syncItcGoalToTracker` and friends).

## Goals follow-up: midpoint + split retrospective (2026-08-26)

Migration `20260826000005_midpoint_and_split_retrospective.sql`.

- **Midpoint check-in is goal-relative, not calendar-fixed.** A guy who joins the app in week 6 or 10 of a quarter still gets a proportional midpoint check-in (or skips it cleanly if there's <3 weeks of runway), instead of missing a fixed calendar week silently. `computeMidpointCheckAt(quarter_end, created_at)` computes the date at goal-create time; the daily cron and render-time checks are trivial date comparisons.
- **21-day floor rule (`MIDPOINT_MIN_RUNWAY_DAYS`).** A midpoint less than 3 weeks from quarter-end is meaningless — the retrospective is close enough. Return `null` and the prompt never surfaces for that goal.
- **ITC goals skip the midpoint entirely.** The ITC map has its own stage-driven cadence (walkthrough, prioritize, test_design, running, results, done). A separate midpoint prompt would be noise. Enforced at goal-create time in `syncItcGoalToTracker` (no midpoint written for `source='itc'`).
- **One freeform field, not a slider or a number.** Quarterly goals are heterogeneous: "deadlift 350" and "communicate better with my team" both live in the same table. A generic progress slider is meaningless for the second kind and a number is meaningless for the first without inventing the metric. Freeform ("Where are you at with it?") works for both and matches the coach voice.
- **Retrospective split into two fields.** `retrospective_what_happened` (concrete story) + `retrospective_what_learned` (extracted lesson) treats quarter-end as a real retrospective instead of a verdict-with-a-note. Verdict (Yes/Partway/No) still lands in `status` but sits below the two text fields in the UI. The old `review_reflection` column stays undropped for now — the split action writes to the new columns and leaves the old one null; a follow-up migration can drop it once we're sure the split fields carry the intent.
- **Retrospective fires 7 days before quarter-end, not on quarter-end day (`REVIEW_LEAD_DAYS`).** Waiting until the calendar boundary meant the coachee had usually mentally moved on. 7 days gives him a full final week with the quarter still live to reflect while the memory's fresh. Prior-quarter goals still transition unconditionally as a safety net for a missed cron run.
- **Partial index on the midpoint prompt trigger.** `quarterly_goals_midpoint_pending_idx` on `(user_id, midpoint_check_at) WHERE midpoint_check_answer IS NULL AND midpoint_check_at IS NOT NULL`. Almost all goals never simultaneously flip to "midpoint due but unanswered," so a partial index keeps the /today + /goals lookups cheap while never bloating.
- **Rejected: AI positive-reframing on the retrospective.** Proposed as idea 3 but pulled. Reflex reframing is exactly the therapist-voice failure mode the Dad Edge voice bans. If a guy writes "I bombed this quarter," a "here's the positive angle" reply gaslights him and teaches him to write reflections that seek validation. If we do add this later, the trigger has to be tight (explicit self-labeling, not "sounds negative"), the coach's job is to correct the overclaim (not reframe), and it never uses the word "reframing" in prompt or UI.
- **Nav promotion for Dashboard + Goals.** Both sit at the top of the desktop SideNav — planning/analytical surfaces above the daily-work items. Neither is added to the mobile BottomNav (5-slot ergonomic cap). Mobile users reach Dashboard via /me's top card and Goals via the "Manage goals" button on /missions.
- **`How you'll know` field dropped after one release.** Added in `20260826000002` alongside `current_state` + `desired_end_state`, then dropped in `20260826000004` after review: if the finish line is written specifically enough, the signal is baked into it. A separate "how you'll know" field only enabled fuzzier finish lines. Coach should push to sharpen the finish line, not add a field to compensate.
- **Voice/tone audit pass.** After the bundle shipped, one comprehensive read-through against `Assets/Voice and Tone/voice-and-style.md`: banned-word grep (clean), tightening of wordy or subtly abstract lines (e.g., "NINETY-DAY HORIZON" → "THIS QUARTER"; "Baseline captured" → "Baseline saved"; "trending compared to last quarter" rewritten to lead with the concrete condition; adaptive empty-state cleaned to match the "Goals" section rename). Every user-facing string on `/goals`, `/goals/[id]`, `/today` goal prompts, `/dashboard` cards, and the `/me` dashboard link was read against the voice guide.

## Coach Context Pipeline (2026-08-27)

Migration `20260827000001_coach_messages_metadata.sql`.

- **Provider pattern over monolithic assembler.** Old `context.ts` was 420 lines that fetched everything in one Promise.all and rendered one string. New shape is `src/lib/coach/context/` with 8 provider files + a small assembler + a registry array. Adding a context source (dashboard-derived trends, ITC status, features not yet built) is now: write one file, append to registry. No changes to assembler, no changes to prompts, no changes to existing providers. Extensibility is the whole point; the throwaway-provider test in `tests/coach/context.test.ts` is the load-bearing proof.
- **Cacheable-first ordering for prompt caching.** The assembler emits two strings: `cacheablePrefix` (identity/family/survey — content that changes weekly at most) and `volatileBody` (goals/missions/streaks/reflections/itc — daily churn). `send-message.ts` places the cacheable prefix immediately after the persona/method prompt and before the volatile body, so Anthropic's stable-prefix caching catches the largest amount of shared bytes across turns without needing explicit cache_control breakpoints. This is a "get it right by structure" choice — the SDK behavior does the caching automatically as long as the shared prefix is the same string.
- **`itc` provider is conditional, not gated by mode.** Returns null when the user has no linked itc_participants row or no in-progress map. Mission-mode and general-mode both get the ITC provider in the pipeline; the null-return keeps ITC-inactive users' contexts clean. This matches the spec's "context is uniform across modes" rule.
- **Survey provider skips the 15-question dump.** Full survey detail was 15 questions × ~30 chars each = ~450 chars of low-signal noise every turn. New shape: composite + delta + only questions where |delta| ≥ 1 (or, on baseline, questions scored ≤ 2 or with substantive notes). Full detail is one follow-up question away. Force-feeding it is context bloat for marginal marginal signal.
- **coach_messages.metadata as the audit trail.** JSONB column, written on the assistant turn insert. Shape: `{context: {providers[], tokenEstimate}, safety: {severity, categories}}`. The "what did the coach know when it said that" question is asked constantly during coaching-quality reviews — this row is the answer. Same purpose `itc_turn_events` serves on the ITC side.
- **Safety enqueue widened to medium.** Old code only enqueued high/critical (crisis). Spec: medium goes into `coach_flags_queue` for admin review with no change to the reply. This is now line 143-154 of send-message.ts. Low/none don't hit the queue — ordinary distress is coaching territory, not queue territory.
- **Allowance rework: never hard-block a marriage conversation.** Old buckets: `ok / warn (at soft cap) / block (at 2× soft cap)`, where "block" threw. New buckets: `ok (0-119) / notice (120-149, quiet indicator at 80%) / over (150-299, explicit "over your allowance" notice but coach responds) / block (300+, runaway-spend safety net only)`. The composer now only disables at `bucket === 'block'` — never at soft cap. Spec's exact framing: "never hard-block a man mid-conversation about his marriage."
- **General mode ships in the same release as mission mode.** Both prompts already existed in `prompts.ts` (systemBase('general') with OTFW method, hedge language, general-mode output contract; systemBase('mission') with the 5-criteria mission bar and single-purpose framing). Both go through the same context pipeline, same safety classifier, same allowance metering, same admin queue. No code difference beyond the mode string; the difference is entirely in the prompt.

  **Rollout recommendation.** Ship mission mode publicly first. Let it accumulate 2-3 weeks of real user traffic + admin-queue review. General mode is riskier because it has no natural "output shape" — a mission-mode reply is scored by whether the mission is concrete, actionable, and grounded; a general-mode reply is scored by "did it help him think about the thing he came here about," which is harder to see going sideways from a single output. Once mission mode has run in the wild and the /admin/coach-flags queue has been reviewed at least once, unlock general mode. This is a product decision, not a code gate; the code ships complete in Checkpoint C.

- **Admin queue filtering.** `/admin/coach-flags` now supports `?severity=` and `?status=` query params (all/medium/high/critical × open/reviewed/all). Default view is `severity=all&status=open` so admins land on outstanding work. Also surfaces the classifier's `flag_reason` string under the message and the conversation's mode badge — small additions that make the queue actually reviewable instead of just a wall of messages.
- **Transcript deliverable via scenario script.** `npm run coach:scenario -- <email> <mode> "<message>"` runs a real coach turn against a seeded user, prints the assembled context (which providers contributed + full context body), the reply, the mission suggestion if any, the crisis verdict, allowance state, and the metadata written to coach_messages. This is how coaching quality gets validated in-loop — the same pattern used for the ITC tool's coach output during that build. See scripts/coach-scenario.ts.

## Main coach voice split from ITC coach (2026-08-27)

New file `docs/main-coach-ai-patterns.md`. Voice-rules loader at `src/lib/coach/voice-rules.ts`.

- **Two-doc composition, not one.** The shared `docs/coach-voice-and-tone.md` is loaded by both coaches. The main coach loads an additional stricter doc (`docs/main-coach-ai-patterns.md`) via the composed `MAIN_COACH_VOICE` bundle. The ITC coach doesn't. Rationale: the ITC coach's voice is calibrated to a scoped surface (drafters + narrow reaction prose about specific map entries) and is working; adding open-conversational-space bans (dramatic openers, manufactured reversals, etc.) would over-constrain it for no gain. The main coach lives in a genuinely open surface (marriage, kids, work, business) and needs the stricter list.
- **Doc-inheritance beats prompt duplication.** Prior state: `src/lib/coach/prompts.ts` had its own PERSONA block that duplicated a subset of the voice doc. Any voice-doc update (e.g., the pronoun-from-context rule shipped 2026-08-26) never propagated to the main coach. New shape: `systemBase()` wraps every mode with `withVoiceRules()`, which prepends the composed bundle. One voice change now lands everywhere the doc is loaded, no drift.
- **Rejected: single doc with per-section flags.** Considered a shape where sections in the shared doc were tagged with something like `<applies to="main-coach-only">`. Rejected: adds parser complexity for one distinction, and blurs the "this is your voice" reading experience. Two docs, one loader that composes, is simpler.
- **Fragment-for-emphasis specifically called out.** Both transcript runs (mission + general) showed the model reaching for stacked-fragment cadence at the close ("Not big. Not performative."). Ban rule updated with concrete before → after rewrites so the model has a target to write toward, not just "don't do this."
- **Em-dash strip at the output boundary (`src/lib/coach/scrub-reply.ts`).** Prompt bans em-dashes but no prompt rule survives every generation. Deterministic scrubber on `reply.reply` before persist + return catches the residual. Deliberately narrow — only punctuation, not deeper voice violations. A scrubber can't tell an earned reversal from a manufactured one; that's a prompt concern.
- **PROMPT_VERSION bumped to v4-2026-08-27** so telemetry can attribute future behavior to the exact prompt after this significant voice change.
